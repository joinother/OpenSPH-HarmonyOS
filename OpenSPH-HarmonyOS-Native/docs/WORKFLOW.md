# 文档维护流程

> 类型：维护规范；更新日期：2026-09-08（Asia/Shanghai）。

## 开发任务的唯一入口

先读 [产品实施路线](reference/PRODUCT-ROADMAP.md)，从第一张前置已通过且未完成的 R 工单开始；一次只推进一张主工单。历史研究中的“下一批”和 P 级优先级不直接派生任务，研究去向统一看 [映射表](reference/RESEARCH-IMPLEMENTATION.md)。

开始时写清工单编号、玩家能完成的步骤和测试门槛；完成后更新同一行状态与证据。若受阻就记录最小复现并继续解决该断点，不以新增皮肤、报表或别的模型代替进度。用户明确改方向时重排该路线，不另建竞争计划。功能交付必须同时包含 UI／CLI、状态恢复及适用的数值／视觉验收；计划中的测试与已通过的证据分别标记。

## 入口与归属

项目 README 只介绍当前能力、边界、构建与验证入口。[文档目录](README.md) 是资料索引，[CLI 指南](CLI.md) 是当前操作规则。新增版本时直接更新当前规则，不把多个版本的相反描述继续追加在指南末尾。

| 目录 | 保存内容 | 更新规则 |
| --- | --- | --- |
| `releases/` | 单版本变更、模型限制与验证记录 | 每版一份；已发布记录仅做标明原因的勘误、链接或格式修复 |
| `research/` | 有来源、日期、取舍的调研快照 | 新结论替代旧方案时，旧方案移入 research/archive |
| `reference/` | 固定上游版本、接口或覆盖审计 | 写明审计范围，更新结论须有新证据 |
| `archive/` | 旧设计、早期验收与旧指南 | 顶部声明历史身份，链接当前入口 |
| `evidence/` | JSON、CSV、TXT 等原始测试和审计证据 | 新结果单独命名；原始数据不为排版而改写 |

工作区 `work/` 为临时脚本、下载和备份，不是当前说明入口。输出目录已有版本 HAP、源码 ZIP 和摘要文件是历史快照；仅整理文档时，不修改应用版本、不重打包旧产物。

## 日期和版本

- 中文正文日期统一为 `YYYY-MM-DD`；需要精确时刻时使用带偏移的 ISO 8601，如 `2026-09-06T17:53:06+08:00`，默认时区 Asia/Shanghai。
- 分开写调研日期、验证日期、发布日期和更新／整理日期。整理日期只证明文档何时整理，不证明功能何时发布。
- 原始日期没有明确记录时写“未单独记录”；不以文件修改时间、目录日期或版本顺序推算发布日期。
- 保留外部来源的发表日期、历史验证日期和原始日志时间戳。移动文件不代表重新调研或重新验收。
- 当前源码版本以 `AppScope/app.json5` 的 versionName 为准。README、CLI 和文档目录同步；历史记录保留其适用版本。
- 版本文件用 `RELEASE-0.12.0.md`；按天的调研用 `TOPIC-YYYY-MM-DD.md`；持续维护的指南采用稳定名称，不给每次修改再复制一份。

## 排版与链接

每份 Markdown 只有一个一级标题，其下按层级组织。标题、段落、列表、代码围栏之间留空行；代码示例标语言，表格使用标准分隔行。文件采用 UTF-8、LF 和末尾换行，无行尾空格或连续三行以上空行。

项目内部用相对 Markdown 链接，便于源码目录独立移动；命令示例中的路径按执行目录表达。外部引用链接到原文。移动资料时修复引用并记录迁移表，不能仅保留裸文件名让读者自行寻找。

## 每次交付

1. 查阅当前入口，确认修改的是指南、版本记录还是历史资料；检查已有主题，优先更新原文。
2. 实现行为变化后同步当前指南、命令目录和必要示例；版本记录写具体变化、适用边界及实际验证结果。
3. 将新证据保存到 `docs/evidence/`，在对应记录中建立链接；区分主机测试、模拟器、真机与科学数值验证。
4. 在项目根目录运行 `python3 scripts/check-docs.py`，修复格式、失效链接和当前版本不一致。
5. 人工核对叙述是否与实现一致、历史结论是否被误当成当前事实。检查器不能判断物理正确性或外部网页是否仍有效。
6. 仅修改文档时，无需重新构建、安装或运行物理测试；修改脚本则检查其语法和实际受影响路径。不得把旧验收写成本轮新通过。
