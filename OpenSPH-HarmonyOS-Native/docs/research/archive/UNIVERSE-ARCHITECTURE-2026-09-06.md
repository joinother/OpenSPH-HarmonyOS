# 全宇宙交互：Universe Sandbox、Celestia 与 OpenSPH 如何分工

> 类型：调研快照；适用范围：历史方案。
> 调研日期：2026-09-06；整理日期：2026-09-06（Asia/Shanghai）。

本文保留当时的判断、限制和操作记录，可能已被后续版本替代。请先阅读[当前文档目录](../../README.md)。

调研日期：2026-09-06。建议扩大产品架构为“宇宙浏览 + 可编辑动力学场景 + 局部高精度碰撞”。Universe Sandbox 用于交互参考；Celestia 值得评估复用星表、坐标、星历与观察者相关模块；OpenSPH 继续承担粒子物理。本文是方案评估，本轮没有引入第三方源码或改变项目许可证。

## 三者的适用角色

| 项目 | 确认的信息 | 建议 |
| --- | --- | --- |
| Universe Sandbox | 官方产品包含引力、碰撞、材料、气候与自建系统；开发采用 Unity，2026 路线图讨论 DOTS 重构 | 参考添加/编辑/投射天体、时间控制、对象面板和实验分享；本轮未找到可供移植的官方开放源码与许可，不把它当源码依赖 |
| Celestia | C++ 开源宇宙可视化；GPL-2.0-or-later；提供星表、坐标、轨道和观察者体系 | 评估选择性复用；它的星历/轨道展示接口不能直接充当碰撞动力学求解器 |
| OpenSPH | 本地已接入真实 SPH；源码包含 N-body 和 Barnes-Hut；应用目前只有三个简单实验 | 扩展统一的场景物理层，先做好轨道，再完善多天体碰撞 |

依据：[Universe Sandbox 功能](https://universesandbox.com/)、[官方架构路线图](https://universesandbox.com/blog/2026/03/universe-sandbox-roadmap-2026/)、[Celestia 主仓库](https://github.com/CelestiaProject/Celestia)。路线图中的未来项目不视为已发布能力。

## Celestia 具体有哪些值得评估的部分

- **跨尺度坐标**：`UniversalCoord` 使用高精度定点坐标，提供相对距离转换。适合研究跨恒星距离导航时，怎样保留近处天体的位置精度。我们的渲染应围绕相机或局部原点表达坐标，不能让全部星系位置直接进入同一套 float 粒子坐标。[当前源码](https://raw.githubusercontent.com/CelestiaProject/Celestia/master/src/celengine/univcoord.h)
- **导航和选择**：`Simulation` 暴露对象搜索、选择、居中、前往、跟随、参考系及多个观察者接口。其职责划分很适合宇宙浏览；鸿蒙交互仍通过 ArkUI 和现有命令入口实现。[当前源码](https://raw.githubusercontent.com/CelestiaProject/Celestia/master/src/celengine/simulation.h)
- **星历与轨道**：`celephem` 包含椭圆/采样/脚本轨道、JPL、SPICE 和 VSOP87 等模块。应先选所需的时间范围和天体覆盖，再核验依赖与精度。[源码目录](https://github.com/CelestiaProject/Celestia/tree/master/src/celephem)
- **天体目录**：ssc、stc、dsc 分别用于太阳系、恒星和深空对象，可参考其分层目录思路；内容包与应用代码分开维护。[项目说明](https://github.com/CelestiaProject/Celestia)
- **移动端桥接**：已有 AndroidCelestia 工程，可以研究原生界面与 C++ 核心的连接和资源组织。Android 实现不是可直接部署到鸿蒙的 ArkTS 实现。[移动端仓库](https://github.com/celestiamobile/AndroidCelestia)

不建议第一步整体合并两个渲染器：Celestia 和现有粒子视口都维护相机、资源、时间与渲染状态，粗暴合并会出现两个世界和两套状态。应先定义共同的坐标、时间、对象标识与显示接口，再决定保留哪一个渲染框架。

## “所有星体都能互动”应如何实现

可实现的产品目标是：用户能浏览大范围宇宙目录，选择支持模型的对象加入实验、修改属性、改变轨道、制造碰撞并保留结果。不能承诺把真实全宇宙的所有天体同时做实时、高精度 SPH 运算。很多目录对象缺乏质量、内部材料等必要数据；补全参数必须标注为估算或用户假设。

建议分三层，以下为本项目设计：

1. **宇宙目录与浏览层**：管理对象目录、名称、资源、位置来源和历元；按需加载。远处对象采用目录、星历或适合的统计模型展示。
2. **活跃动力学层**：用户选中的系统采用 N-body 等模型，支持轨道扰动、捕获、合并和简化碰撞。外部引力采用明确的边界/近似模型，不能因为不在画面内就自动消失。
3. **局部碰撞层**：需要形变和碎裂的区域使用 OpenSPH。计算耗时较长时允许异步计算、回放观察。高级星体类型需要对应材料/状态方程，不能统一套用岩石模型。

初期采用显式“加入实验”和“创建碰撞实验”的方式切换。等数值与数据转换验证充分，再评估自动精度切换。SPH 和 N-body 之间的升降级需要守恒、能量分配和碎片识别，不是根据镜头距离切换一个渲染 LOD 就完成了。

## 最重要的连接工作

以“从星图选地球与月球，改变月球速度，观察撞击”为验收流程：

- 在同一历元获取对象状态，统一时间尺度、参考系、位置和速度单位。
- 从目录对象创建实验实例，保留来源和假设，给实例独立 ID。后续动力学接管该实例，不能再被原星历每帧覆盖。
- 初期先运行可验证的轨道模型；用户触发局部碰撞实验时，再生成满足质量、质心、线动量和自转约束的粒子初始条件。
- 返回结果时，明确当前是原始对象、原始材料来源，还是识别出来的新碎片。碎片必须有自己的身份。
- 保存实验分支和计算结果；返回浏览界面时，用户可以保留修改后的系统，或切回原始目录状态。

建议为对象状态标明 `catalog / ephemeris / nbody / sph / replay` 来源，并由同一服务管理。CLI 与 UI 共同使用对象查询、加入实验、编辑属性、开始计算、保存分支等操作。现有 ArkTS + C++ 分工仍然适用。

## 直接引入 Celestia 源码的许可影响

Celestia README 声明 GPL 第 2 版或更高版本。若直接复制并集成其 GPL 代码形成派生/组合程序，发布时需要履行相应 GPL 许可和源码提供义务；不能只沿用本项目当前的 MIT 标签。分出一个动态库并不能单独证明程序彼此独立。[许可证](https://raw.githubusercontent.com/CelestiaProject/Celestia/master/COPYING)

CelestiaContent 要求另查 README 或逐文件 `.license`；星表、纹理、模型不能一概按主程序许可处理。[内容许可说明](https://raw.githubusercontent.com/CelestiaProject/CelestiaContent/master/LICENSE.md)

可选路径：一是接受相应 GPL 发布方式后选择性移植核心；二是依据公开算法和自有实现建立导航/坐标层，按各自许可使用天文数据。当前先完成候选模块、依赖和内容许可清单，尚不改变现有项目的许可。

## 推荐推进顺序

A. 先建立统一 SceneDefinition、天体 ID、单位、历元及状态来源，扩展对象编辑与实验库。

B. 做一个小而完整的太阳系浏览与两体/多体轨道场景，验证浏览状态转为可编辑实验后不会跳回原轨道。

C. 把选中的对象接入现有碰撞实验，建立质量/动量、尺度变换和存档回放测试。

D. 在上述流程稳定后扩大星表、目录分块和细节层级，再推进星系近似模型、气体、潮汐与其他独立物理能力。

优先让一套太阳系真正可浏览、可修改、可碰撞、可保存，再扩大宇宙覆盖范围；目录规模与同时活跃的精细求解规模应分别设预算。
