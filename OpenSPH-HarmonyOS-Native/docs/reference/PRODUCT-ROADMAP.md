# 产品实施路线

> 类型：唯一执行路线；重排日期：2026-09-08（Asia/Shanghai）；状态更新：2026-09-09（Asia/Shanghai）；源码基线：0.56.0。R01 已完成验收基线，未新增应用功能，完整碰撞玩法仍未通过。

## 先做出什么产品

第一阶段做成一个能反复游玩的天体碰撞沙盒：**在星图加入岩体 → 调整轨道或瞄准发射 → 撞击与破碎 → 在同一世界观察残骸 → 残骸继续受引力运动 → 再加入天体 → 保存后继续。**

第一条完整流程先限定在现有受支持的小岩体尺度。通过后，才扩展到卫星摄动环、分层行星，最后推进星系／天空变化。小岩体流程不能作为“整颗地球碰撞”交付；后者必须通过单独的行星初态与材料门槛。

**R01 已完成，当前唯一可开始的工作是 R02。** 后续严格按 R03 → R04 → R05 → R06 推进。R06 通过才算第一个核心玩法完成。新增版本、统计字段、截图或测试数量都不替代这条完整流程。

## 为什么要重排

旧 P1–P5 描述了模块，缺少明确的下一张工单、完整玩法验收和停止支线的规则。结果是轨道、局部 SPH、环和星系各有能力，却没有统一的对象、时间与返回结果；界面增加了很多解释，但玩家仍无法让撞后的世界继续运行。

0.54–0.56 的局部撞击、潮汐与来源统计都是可复用基础；问题在于它们被逐项当成了产品进度。此次把原 P1–P5 降为需求分类，以下 R 编号才是执行顺序。历史调研中的 P0/P1 等优先级仅代表当时建议，不再直接驱动开发。

## 路线选择

| 可走的方向 | 好处 | 当前代价 | 决定 |
| --- | --- | --- | --- |
| 继续扩大星空、贴图、星系和预设 | 很快能展示更多画面 | 碰撞与连续世界的断点仍在 | 暂停扩展，现有功能只修回归 |
| 先完整复刻大型宇宙模拟器 | 覆盖愿景广 | 天文导航、行星材料、气体、星系和运营同时展开，无法形成可验收的小交付 | 不作为近期计划 |
| 先完成受支持岩体的连续碰撞玩法 | 直接解决放置、撞击、观察、继续玩的断点，可复用现有代码 | 需要处理对象身份、事件时钟、双向受力及残骸转换 | 采用；以 R06 为首个完整里程碑 |

这次取舍依据用户反复提出的放置／撞击／一镜到底／环问题，以及[公开创作者样本](../research/TARGET-CREATOR-651227816-2026-09-08.md)的搭建系统、材料去向、卫星互动和过程创作需求。样本只有一个账号，旧调研未播放视频，不能当成普遍用户偏好统计。各专题如何归入主线见 [调研到执行的映射](RESEARCH-IMPLEMENTATION.md)。

## 操作逻辑的共同设计

2026-09-09 用户要求重新审视整个应用的名称、布局与使用方式，已形成 [交互设计契约](../design/INTERACTION-DESIGN.md)。该方案按“选场景 → 点天体 → 对它操作 → 看结果”组织，区分显示／物理编辑、实时／回放、保存设置／回放／进度；23 项主题名称和高风险按钮已有迁移清单。依据是当前代码、只读现场与 R01 证据，尚未接入应用或完成用户测试。

这项明确需求纳入原队列：R02 先改首批易误解文案与状态／保存／返回语义；R03 落地对象操作、放置和面板结构；R07 完成分类、剩余文案与视觉统一。不能将所有操作问题都推到 R07，也不跳过事件与世界正确性的前置。每张工单同时执行交互契约中的相应任务验收。

## 当前交付与下一步

### R01：已完成固定验收流程

[验收协议](CONTINUOUS-COLLISION-ACCEPTANCE.md)集中记录固定输入、共享 UI／CLI 入口、逐步判据、恢复约束和证据。两轮 G1–G3 的实际配置与初始世界逐字段一致，G2 只编辑横向偏移；[独立核对](../evidence/r01-baseline-2026-09-08-verified/analysis.json)通过。

G1／G3 的放置、接触和至少 60 秒局部材料演化通过，连续观察、同步世界、残骸提交、撞后再加入与重开续算不支持。G2 在至少 90 秒内无接触，普通轨道可保存重开续算；其残骸步骤未测。121 项主机检查通过，指定模拟器初始暂停场景及 13 个原持久文件已恢复。本张没有增加应用功能，也未执行新的科学收敛或真机测试。

### R02：先解决撞击发生在哪个世界时刻

代码入口：`orbit.cpp` 的接触漂移／半步推进、`orbit_session.inc`、`Engine::startImpact`／`ImpactReturn`，以及 `impact_session_test.cpp`。当前 `contact.world` 虽保存事件瞬间全部天体，但速度属于积分子步阶段；当前返回会话则是显示出来的反弹后状态。二者不能混成同一份可续算世界。

本张先写状态转换表，再实现：待选择、准备、局部运行、可提交、已提交、已放弃；记录唯一事件身份、所属世界修订和积分阶段。用不同于现有观察回放的新会话格式保存稳定边界；不把 v20 改称 SPH 求解器检查点。转局部路径不先消费弹性冲量，选择硬球路径才执行原响应；放弃回到约定的待选择事件状态。

测试先于开放入口：同一事件提交两次、旧修订启动、写入中断、应用重启、准备取消／失败、半步↔完整步转换、旧硬球模式回归。首批文案、完成／回放主操作、取消与返回目的地按交互契约核对，UI 与 CLI 共用标签。第一版只承诺事件待处理和提交后这两个稳定边界可恢复；中途 SPH 的精确断点续算另列后续项。稳定边界恢复不能静默重算一份不同结果。

### R03：让模型转换留在同一个视口

代码入口：`renderer.cpp`、`camera_journey.h`、`Engine::fragmentFrame`、`Index.ets`。用 R02 的事件参考系映射局部位置与整体质心运动；保留外部天体，不能用整幅重置镜头掩盖模型切换。选择的是同一对象或其后继材料，不能依赖变化后的数组索引碰巧相同。

先验证坐标、对象身份与绘制状态，再做过渡。相机切换与折叠旋转期间不增加求解请求、不重置时间；初态粒子包络与源球半径对应。录制本应用的屏幕／截图作观察验收，CLI 单独核对状态。此张可改善“一镜到底”，但只有 R06 后才能宣传撞击后继续整个世界。

## 测试与放行规则

| 层级 | 如何测 | 什么情况下不能放行 |
| --- | --- | --- |
| 数据与事务 | 单位转换、稳定对象身份、事件状态机、保存原子性、重复／过期请求、坏档；独立断言预期世界 | 取消或失败改变世界；重复提交；数据不完整却报告成功 |
| 物理转换 | 对总质量、线动量、角动量和来源逐项记账；角动量包含残骸内部自旋；转换损失需进入明确的内能／未解析项 | 只保留最大几个碎片；内部角动量直接消失；用渲染 float 或几何标签代替真实状态 |
| 数值模型 | 已知解／对称性、无外源对照、不同步长／粒子预算／种子；完整能量项与边界功分别记录 | 没有独立参考；降低阈值去迎合失败；只凭画面或最后一帧宣称束缚、熔融或收敛 |
| 应用流程 | G1–G3 状态与结果断言，公共按钮／输入绑定和 CLI 回归；首次失败保留原始输出 | 功能后半段跳过；模拟器通过冒充真机；CLI 通过冒充触摸或动画通过 |
| 视觉与设备 | 手机、平板、折叠展开／收起、横竖屏、PC 窗口；检查视口、状态栏、底部手势区、对象可见与过渡中断 | 必要操作被遮挡、旋转重算／丢状态、近看丢太阳、背景与模型发生可见跳变 |

守恒门槛分开制定：纯坐标／汇总转换先采用质量相对误差 ≤ 1e-10，线动量和角动量按测试夹具的非零物理尺度归一后 ≤ 1e-10；零总量不能直接作分母。积分误差另在 R04 的独立基线中固定阈值并写入夹具，至少三个逐次减半步长；不能把转换精度当成 SPH 积分精度。空间分辨率不稳定的碎片结果只能标为探索演示。

R05 的交接必须读取真实双精度粒子位置、速度、质量、内能及所需材料状态，现有 v20 只有质量／来源和观察摘要，不够重建求解状态。未束缚材料和仍受压力／应力显著作用的材料不能强制变刚球；保留计算表示或拒绝提交。R06 容量不足时保留当前世界并说明原因，不能删除质量、偷偷变无质量或临时忽略引力。

性能测量要分别给出准备时间、求解吞吐、界面帧时间、内存和取消响应。交互目标为准备期间仍能操作、取消反馈目标 1 秒内、测试设备视图帧时间 p95 目标 ≤ 33.3 ms；这些是拟定目标，不是已测结果，不要求 60 秒物理演化在 60 秒墙钟内完成。真机确认前不对手机算力作保证；图形降级与求解预算分开，降求解预算需要显式选择并保留模型配置。

## UI、物理和存档的共同约束

每张功能工单都包含自己的界面入口、CLI、存档兼容和测试，不再采用“先做十个底层功能，以后一起接界面”的方式。实现优先沿用 ArkTS/ArkUI 控件、C++ 物理与同一 XComponent 渲染场景，不整体重写已验证的模块。

UI 规则：星图是主要工作区；高频放置／暂停／跟随在视口边缘，细节按当前对象展开；一个操作只保留必要面板；停止、取消和返回必须语义清楚。R03 解决过渡与身份，R07 才集中整理表面、菜单密度和视觉一致性。每次都检查沉浸式和折叠旋转，不另开一条没有截止点的“年轻化 UI”支线。

物理规则：先正确的事件和受力，再残骸，再热表面，再扩展材料。第一版只允许一个活跃的局部碰撞域；多域同时碰撞需要明确暂停／拒绝行为，不静默漏算。R04 的内部坐标表示与多速率积分需在该工单原生验证后定稿，世界状态与时间契约先固定，不能直接在冻结潮汐上拼一个计时器冒充双向演化。

## 每次工作的固定节奏

1. 开始时读本页，报告当前工单、用户可见结果和本次通过条件；不再从旧专题随机挑功能。
2. 一次只推进一张主工单。可以在一次会话内完成它并顺序推进下一张，但前一张必须先通过验收并更新证据。
3. 每张工单按“最小复现／测试设计 → 实现 → 原生验证 → 应用流程 → 视觉与适用设备 → 备份恢复”收尾；不适用的层级写明原因。
4. 若工作受阻，记录具体失败与下一次最小验证，继续解决同一断点；新发现进入对应后续行，不立即切换主线。用户明确改变优先级时才重排。
5. 交付报告只写：工单状态、玩家新增能完成的步骤、实际测试与失败项、下一个工单。局部通过写局部通过，不用测试数量冒充里程碑完成度。
6. 状态、顺序只在本页维护；专题负责证据与技术细节，版本记录负责历史。开发断点可正常提交，但不因一个字段而宣称一个玩法里程碑完成；纯计划整理保持应用版本和已有产物不变。
